# Why: なぜ"GLSL"か?

## GLSLとは

まず、`GLSL`は`GPU`上で動作する`シェーダ`と呼ばれるプログラムを記述するための**用途専用の言語**の1つです。`openGL Shading Language`の略で、名前の通り`OpenGL`という**グラフィックライブラリ**(の頭文字を取って`GL`ですが)で使用するために**定義**[^glslwhydef]された言語ですが、今日では`OpenGL`に限定されずもう少し広い範囲で対応する実装があります。

## MinecraftでのGLSL

「`GLSL`がなぜ`Minecraft`で出現するか」という問いに対して、「`Minecraft`が`OpenGL`で動いているから」という理由は**もう**[^glalreadyno]**正しくありません。**\
先に記した通り、`Minecraft`以外の文脈でも、`GLSL`は`OpenGL`に**限定されるものではない**のです。

ですから、正確には「**`Minecraft`のリソースパックが受け取るシェーダ言語の形式が`GLSL`だから**」と言えます。

今回やろうとしていることは**シェーダの書き換えで実現可能**です。なので、`GLSL`を書くのですね。

## じゃあやってみてよ

ところで、`リソースパック`はMinecraftの画面に表示される個々の要素、例えば「**テクスチャ**」と呼ばれる**画像**や、「**モデル**」と呼ばれる**3D形状**などを差し替えるために使用できるものであることは知られています。

そして、差し替えることができるものの1つに、ゲームが使用する**シェーダ**も含まれます[^shadersecurity]。

**シェーダ**はゲームの各要素が画面に描画されるとき、その**頂点の座標**の計算と画面に**表示する色**を計算するために、`GPU`上で動作する**プログラムの呼び方**[^caniuseshader]です。

どの**シェーダ**を差し替えることができるかは`Minecraft`のバージョンにかなり依存しますが、画面に描画する**文字全般**のシェーダは少し前のバージョンでは`assets/minecraft/shaders/core/rendertype_text`あたり、`26.3`では`assets/minecraft/shaders/core/text`で差し替えが可能です。

試しに、文字の読み込みをなくして単にその場所を`#00ff00`、アルファ値`20%`に塗りつぶすように書き換えてみると、下のようになります。

# Primitively: 原始的には文字色はただの数値

少し計算機(コンピュータ)の**原始的な話**をします。**原始的な**というのは時代の話ではなく、**原理的な基礎**についてのことです。\
$_{(この章では10進数での説明をしますが、10以外の基数で読み替えてもらっても構いません。}$$_{ピンと来なければこの行は見なかったことにしてください。)}$

まず、現代の計算機、例えばパソコンやスマホなどいわゆる「**デジタル**」なもの[^classicalcomputer]は、すべて**決まった桁数の正の整数**のみをデータとして扱うことを前提にしています。

例えば、「**1桁**」と言えば`0`から`9`の`10通り`のいずれかの状態であることを示します。「**2桁**」なら`0-99`の`100通り`、$...$「**10桁**」と言えば`0`から`9999999999`までの`100億通り`、$...$のように、データとして保存したり通信できるのは実は**原始的にはこの仕組みしかありません**。[^zerodigits]

:::details Really: "本当に"それだけしか扱えないの??

「原始的には」はい、「実用上は」いいえです。

実用上、小数を扱いたいときのことを考えます。`abcd`「4桁」の状態を「小数」として解釈したいならば、例えば、 **この場所に「`abcd`」があったら、「`ab.cd`」と読め!** という規則を持つことになります。`2533`という4桁があったならば、技術者はそれを「`25.33`」という数値として解釈するようにします。これはその4桁が小数になったのではなく、**ただ技術者が勝手に小数点を頭の中で書き足して考えているだけ**で、データ自体がそれを小数だと区別しているわけではないのです。

実用上、負の数を扱いたいときのことを考えます。`abcd`の「4桁」の状態を「正または負の整数」として解釈したいならば、例えば、 **aが1なら正、2なら負で、`±bcd`として読め!** という規則を持つことになります。例えば`2533`という4桁があったならば、技術者はそれを「`-533`」という数値として解釈するようにします。これはその4桁が負数になったのではなく、**ただ技術者が勝手に符号を頭の中で書き足して考えているだけ**で、データ自体がそれの正負を区別しているわけではないのです。

:::

**桁数**を決めるのは**技術者の仕事**です。技術者は「**その場面で必要十分な桁数**」を考慮してその**情報を表現するための桁数**を決めます。余分に取ることも少なくない[^howdigits]ですが、現実のデータは**表せる桁数の合計**(=メモリの量[^memorydigits])が決まっていますので、むやみに増やすのはよろしくありません。

## 文字の色というデータ

ところで、`Minecraft`では文字色を`#xxxxxx`という7文字で指定することができます。ここで`x`は`0` `1` `2`..`7` `8` `9`, `a` `b` `c` `d` `e` `f`の16文字のいずれかで、例えば`#e577fc`といった形式になります。$_{(PC好きには馴染みのある形式ですね)}$

この7文字がどうやって色として解釈されるのかは説明しません。重要なのは**これが文字描画シェーダに渡されるということ**ですが、
もっと重要なのは**これが文字描画シェーダに渡せるデータのすべて**となることです。これ以上のデータは文字描画シェーダには**一切渡すことができません**。[^nomoredata]

細かい説明は省きますが、シェーダ側では色のデータを`0`から`16777215`までの`16777216通り`のデータとして扱うことになります。桁数で言うと`8桁より多く9桁より小さい`[^justdigits]データですね。

私の実装では、この数字を数桁ごとに`x座標,y座標,文字サイズ,文字色,通常体か太字か`に分割して解釈するのですが、これだけのデータを **`せいぜい9桁`に収めきる必要があります**。これを実現するイメージを掴んでもらうために**時刻データの例**を示します。

---

時刻について、みなさんは「`AB時CD分EF秒`」という形式を理解できると思います。例えば、「`07時34分24秒`」というようなものです。

これを1つの数値にするとき、`ABCDEF`という形式で、`073424`というように`6桁`のデータとして表現することができるのはご理解いただけると思いますが、実は**このデータの表し方はデータ量として無駄だらけ**です。

なぜなら、時刻データは`24時間*60分*60秒=86,400通り`しかないはずなのに、`6桁`のデータは本来`1,000,000(100万)通り`のデータを表せるはずで、データの本来の表せるうちの`91.3%`は時刻を表現するとき使用されず、無駄になっています。

よって、**データの量を節約したいのならば**単純に`時に2桁、分に2桁、秒に2桁`という割り当て方は**賢くありません**。

そこで、`0時0分0秒からの経過時間(秒)`で表すことを考えます。例えば`07時34分24秒`ならば`27264`といった具合です。

この2つの形式の変換は以下の式で行うことができます:
(ここで`/`は割り算の商の整数部分、`%`は割り算の余りを求めることを示します。)

```:時刻形式 から 経過時間秒 を求める
(経過時間秒) = 3600 * (時) + 60 * (分) + (秒)
```

```:経過時間秒 から 時刻形式(時分秒) を求める
(時) = (経過時間秒) / 3600
(分) = ((経過時間秒) / 60) % 60
(秒) = (経過時間秒) % 60
```

これらの式がなぜこうなるかの説明はしませんが、計算すると確かに変換ができ、**同じことを表現するのに必要なデータの量を減らせた**ことがわかるはずです。

## シェーダに渡すデータの選別

私の実装ではシェーダに`x座標,y座標,文字サイズ,文字色,通常体か太字か`の5つを`#xxxxxx`として渡しています。これらはそれぞれ:

- X座標 `0-255` 256通り
- Y座標 `0-127` 128通り
- 文字サイズ `0-3` 4通り
- 文字色 `0-7` 8通り
- 通常 or 太字 2通り

の割り当てになっており、全部で`2097152通り`です。

...なんとこれは本来表せるはずの`16777216通り`には到底及ばないのですが、これで渡すデータの全てにしています。
次の章で、なぜ残りの`87.5%`は無駄にしたのかという話をしていきましょう。

# Binary: それはゲームの文字か? 私の文字か?

ところで、私はtitleコマンドの描画を変更しようとしていました。\
そのために、`assets/minecraft/shaders/core/text`という**シェーダ**をリソースパックで上書きするのでしたね。

## シェーダファイル: `text.vsh / text.fsh`とは

これらのファイルは、Minecraftが文字を使用されるときに使用される**シェーダ**ですが、ここで重要なのは**このファイルを書き換えるとゲーム内の全ての文字の描画が変更される**ことです。

そして、**シェーダからこの文字が一体何なのかを知る方法はほとんどありません。**\
このままでは、titleコマンドの描画のみを変更する事はできず、すべての文字を本来の位置と異なる位置に描画してしまうことになります。

つまり、上の仕組みをそのまま実装すると、下の画像のようになります。

1. `gold`と`経験値関係の色`以外の色は**R,G,Bのうちどれか2つは必ず等しい**
2. `gold`と`経験値関係の色`は**Bが`0.5`より小さい**

という**2つの条件でこれらの色を区別する**ことを思いつきます。

つまり、色をデータとして渡すとき、上の2つの条件は**逆に満たしてはならない**ことになります。これを満たすために、`87.5%`を無駄にする必要がありました。

これは以下のGLSLコードが判別するために動いています

```glsl
// Color[0.,1.]をiColor[0,255]に変換
ivec4 iColor = ivec4(Color*255.);
// 判定
// ここでは、(x & 128) == 128 は x >= 128 と同等です
if((iColor.z&128)==128&&all(bvec3(iColor.x!=iColor.y,iColor.y!=iColor.z,iColor.z!=iColor.x))){
  // 色はデータ
  ...
}else{
  // 色は本来の色: Minecraft本来の描画を維持
  ...
}
```

[^glslwhydef]:
    「定義」という呼び方に違和感を覚えたかもしれませんが、これは`OpenGL`及び`GLSL`が**特定の実装**を示す単語ではないことと関係します。\
    `OpenGL`と`GLSL`はクロノスグループが「この仕様を定義するからみんな使ってね!」と言って公開された「ライブラリの仕様書」です。仕様書には「この手続きをすると画面にはこれが表示されて状態がどう変化する」という内容が連ねてありますが、そこには「その動作をどう実現するか」は含まれていません。\
    これはなぜかというと、`GPU`というデバイスは**特定の**回路構造を示すものではなく、**異なるGPU**で**同じ動作**をするために**同じ手段**では実現できないためです。\
    そのため、「動作を実現する」方法は`GPU`の開発元が主に**ドライバ**に仕様書の動作を再現した**個別の実装**をします。
    よって、`OpenGL`や`GLSL`を **"定義"**という言い方をするのですね。\
    \
    余談ですが、`OpenGL`のバージョン`1.0`の仕様書は1992年に発表された化石です。このバージョンには`GLSL`は存在せず、`GPU`で三角形をたくさん描画するのが主目的と言うのは流石に過言ですが限定されたことのみができる仕様でした。\
    2004年にバージョン`2.0`と`GLSL`のバージョン`1.0`が発表され、このあたりから本格的にGPUで動作するプログラムをプログラマが自由に書けるようになってきます。(要出典、まだワイ生まれてない)\
    しばらくの間、`Minecraft`は`OpenGL`の上に実装されていましたが、2026年にこれがクロノスの`Vulkan`というライブラリに移行しました。\
    `OpenGL`と`Vulkan`は外側から見るとよく似た役割をしますが、仕様書として設計思想が大きく異なるため、この話も掘り下げたいのですがここではこれぐらいにしておきますね。

[^shadersecurity]:
    プログラムをリソースパックで差し替えられるということはそこに悪意のあるソフトウェアを仕込むことができてしまうのではという危惧は**シェーダというプログラムの性質を理解しないと正しくありません**。\
    シェーダはご承知の通りGPUで実行されます。ここで、シェーダが実行される**GPU上の計算領域**は、「**CPUに与えられたもの以外何もアクセスできない**」状態で実行されます。\
    つまり、CPUが**何も与えなければ**メモリから値を読み込むことも、メモリに値を書き込むことも、自分が動いているかを知ることも、**シェーダは何もできません**。\
    **画面への描画**を目的とした`GPU`の使用では、一般的な悪意のあるプログラムが行うような「インターネットへのアクセス」や「ファイルの読み書き」などは発想やハックの問題ではなく第一に妄想になります。\
    ですので、せいぜい「無駄な計算をしてフレームレートを下げる」や「地形の描画を黒色にして見えなくしまう」ぐらいがシェーダに含めることができる悪意のほぼ限界です。(後者は地形を描画するためのデータと画面への書き込み方法をCPUに与えられる必要があります)\
    \
    ただし、これらは「**シェーダが本当にCPUに割り当てられたことしかできない**」限り正しいです。つまり、GPUやそのドライバに何らかのバグがあってこの境界を超えることができるならば、確かに一般的な悪意のあるプログラムと同様に危惧するべきですが、これを「**`.exe`ファイルをむやみに実行するな**」のような話と同列に語るのは少し難しいので、単に「**プログラムを差し替えられるのが危険**」と言うのは**誤りです**。
