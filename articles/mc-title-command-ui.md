**リソースパック**と**title**コマンドの開拓です。

**対象の読者**: この記事は**用語**と**背景の説明**を含みます。**理解**が目的なら`Minecraft`の`リソースパック`と`コマンド`に触ったことがある程度の知識で**十分読めるはずです**。ただし、**応用**したければ`GLSL`という`GPU`で動作する癖強言語$_{(偏見)}$に慣れ、強烈な技術制約をハックする魔術テクニックが必要になりますが、これらはこの記事では扱いません。

これは**技術解説**です。**↓** のような最早何でもありな`title`を表示することを目標にします。

![](https://static.zenn.studio/user-upload/b1e5680c87cb-20260920.png)

上の描画は **_1. 文字サイズ 2. 文字の表示位置/ルビ 3. 文字色/透明度 4. 字間/行間_** をおよそ自由に表示しています。これを単一のtitleコマンドで実現してしまう技術になります。subtitleすら使用していません。\

**データパックやModなどは使用しません。**\
ただし、同様の方法でコマンドブロックの上限以上の長さが必要な場合はデータパックが必要になります。

この実装をした`Minecraft`のバージョンは`JE26.3`ですが、同等の実装はもう少し前のバージョンから可能なはずです(私の記憶では1.20あたりで可能でした)

# Why: なぜ"GLSL"か?

## GLSLとは

まず、`GLSL`は`GPU`上で動作する`シェーダ`と呼ばれるプログラムを記述するための**専用の言語**の1つです。`openGL Shading Language`の略で、名前の通り`OpenGL`という**グラフィックライブラリ**(の頭文字を取って`GL`ですが)で使用するために**定義**[^glslwhydef]された言語ですが、今日では`OpenGL`に限定されずもう少し広い範囲で対応する実装があります。

## MinecraftでのGLSL

「`GLSL`がなぜ`Minecraft`で出現するか」という問いに対して、「`Minecraft`が`OpenGL`で動いているから」という理由は**もう**[^glalreadyno]**正しくありません。** 正確には「**`Minecraft`のリソースパックが受け取るシェーダ言語の形式が`GLSL`だから**」と言えそうです。

今回やろうとしていることは**シェーダの書き換えで実現可能**です。なので、`GLSL`を書くのですね。

## じゃあやってみてよ

ところで、`リソースパック`はMinecraftの画面に表示される個々の要素、例えば「**テクスチャ**」と呼ばれる**画像**や、「**モデル**」と呼ばれる**3D形状**などを差し替えるために使用できるものであることは知られています。

そして、差し替えることができるものの1つに、ゲームが使用する**シェーダ**も含まれます[^shadersecurity]。

**シェーダ**はゲームの各要素が画面に描画されるとき、その**頂点の座標**の計算と画面に**表示する色**を計算するために、`GPU`上で動作する**プログラムの呼び方**[^caniuseshader]です。

どの**シェーダ**を差し替えることができるかは`Minecraft`のバージョンにかなり依存しますが、画面に描画する**文字全般**のシェーダは少し前のバージョンでは`assets/minecraft/shaders/core/rendertype_text`あたり、`26.3`では`assets/minecraft/shaders/core/text`で差し替えが可能です。

試しに、文字の読み込みをなくして単にその場所を`#00ff00`、アルファ値`20%`に塗りつぶすように書き換えてみると、下のようになります。

[^kyakuchu]: これが脚注です。

[^glslwhydef]:
    「定義」という呼び方に違和感を覚えたかもしれませんが、これは`OpenGL`及び`GLSL`が**特定の実装**を示す単語ではないことと関係します。\
    `OpenGL`と`GLSL`はクロノスグループが「この仕様を定義するからみんな使ってね!」と言って公開された「ライブラリの仕様書」です。仕様書には「この手続きをすると画面にはこれが表示されて状態がどう変化する」という内容が連ねてありますが、そこには「その動作をどう実現するか」は含まれていません。\
    これはなぜかというと、`GPU`というデバイスは**特定の**回路構造を示すものではなく、**異なるGPU**で**同じ動作**をするために**同じ手段**では実現できないためです。\
    そのため、「動作を実現する」方法は`GPU`の開発元が主に**ドライバ**に仕様書の動作を再現した**個別の実装**をします。
    よって、`OpenGL`や`GLSL`を**定義**という言い方をするのですね。\
    \
    余談ですが、`OpenGL`のバージョン`1.0`の仕様書は1992年に発表された化石です。このバージョンには`GLSL`は存在せず、`GPU`で三角形をたくさん描画するのが主目的と言うのは流石に過言ですが限定されたことのみができる仕様でした。\
    2004年にバージョン2.0と`GLSL`のバージョン`1.0`が発表され、このあたりから本格的にGPUで動作するプログラムをプログラマが自由に書けるようになってきます。(要出典、まだワイ生まれてない)\
    しばらくの間`Minecraft`は`OpenGL`の上に実装されていましたが、2026年にこれがクロノスの`Vulkan`というライブラリに移行しました。\
    `OpenGL`と`Vulkan`は外側から見るとよく似た役割をしますが、仕様書として設計思想が大きく異なるため、この話も掘り下げたいのですがここではこれぐらいにしておきますね。

[^glalreadyno]: 2026/9時点の予測、 **「もう」正しくない**と言ったのは、Minecraftはリリース当初からつい最近まで`OpenGL`で動いていたのですが、26年の2月に公式がアナウンス[^linkvulkanannouncement]し、同年4月にスナップショット版に実装された[^linkmc26-2]ように、`Minecraft`はもう`OpenGL`に**限定される**ゲームではなくなりつつあるためです。

[^linkvulkanannouncement]: https://www.minecraft.net/ja-jp/article/another-step-towards-vibrant-visuals-for-java-edition

[^linkmc26-2]: https://www.minecraft.net/ja-jp/article/minecraft-26-2-snapshot-1

[^shadersecurity]:
    プログラムをリソースパックで差し替えられるということはそこに悪意のあるソフトウェアを仕込むことができてしまうのではという危惧は**シェーダというプログラムの性質を理解しないと正しくありません**。\
    シェーダはご承知の通りGPUで実行されます。ここで、シェーダが実行される**GPU上の計算領域**は、「**CPUに与えられたもの以外何もアクセスできない**」状態で実行されます。\
    つまり、CPUが**何も与えなければ**メモリから値を読み込むことも、メモリに値を書き込むことも、自分が動いているかを知ることも、**シェーダは何もできません**。\
    **画面への描画**を目的とした`GPU`の使用では、一般的な悪意のあるプログラムが行うような「インターネットへのアクセス」や「ファイルの読み書き」などは発想やハックの問題ではなく第一に妄想になります。\
    ですので、せいぜい「無駄な計算をしてフレームレートを下げる」や「地形の描画を黒色にして見えなくしまう」ぐらいがシェーダに含めることができる悪意のほぼ限界です。(後者は地形を描画するためのデータと画面への書き込み方法をCPUに与えられる必要があります)\
    \
    ただし、これらは「**シェーダが本当にCPUに割り当てられたことしかできない**」限り正しいです。つまり、GPUやそのドライバに何らかのバグがあってこの境界を超えることができるならば、確かに一般的な悪意のあるプログラムと同様に危惧するべきですが、これを「`.exe`ファイルをむやみに実行するな」と同列に語るのは少し難しいですね。

[^caniuseshader]: 最近のシェーダは画面に描画しないただの数値計算をすることもできますが、今回は扱いません。
